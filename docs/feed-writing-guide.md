# 새 소식 피드 작성 규칙

이 문서는 다섯 감시 작업이 범주 파일의 `feed` 기록과 범주 요약 필드(headline, body, unknown, gap)를 쓸 때 따르는 문장 규칙입니다. README에 적힌 게시 계약(필드, 길이, 시각, URL 제한)은 바뀌지 않으며, 이 규칙은 계약을 통과한 문장이 화면에서 어떻게 읽히는지를 다룹니다. 감시 작업의 지시문에 그대로 붙여 넣을 수 있는 문안과 범주별 고쳐 쓴 예시는 [docs/feed-writing-prompts.md](feed-writing-prompts.md)에 있습니다.

이미 게시한 기록은 고쳐 쓰지 않습니다. 이 규칙은 새로 쓰는 기록부터 적용하며, 수치나 판단을 바로잡을 때는 지금처럼 kind가 '정정'인 기록을 새로 추가합니다.

## 화면에 놓이는 위치

| 필드 | 화면 위치 | 써야 할 내용 |
|---|---|---|
| kind | 범주 이름 옆의 작은 꼬리표 | 아래 여섯 어휘 가운데 하나 |
| title | 굵은 제목 | 이번에 확인한 핵심 변화 한 가지 |
| text | 제목 아래 본문 | 무엇이 어떻게 바뀌었는지 설명하는 2–4문장. '변화 없음'은 한 문장, '확인 제한'은 한두 문장 |
| evidence | 접힌 '확인 방법' | 조회 시각과 확인 방법, 출처 사이의 차이, 이 기록을 읽을 때 알아야 할 확인 한계를 이 순서로 담은 세 문장 이하, 250자 이내의 글 |
| sources | 접힌 '출처' 목록 | 본문을 직접 뒷받침하는 공개 URL |
| headline, body | 범주 타일의 제목과 본문 | 지금 상황의 핵심과 설명 |
| unknown | '다음 확인' 목록 | 공식 인증이나 피해 기관의 확인처럼 바깥에서 아직 정해지지 않은 사실 |
| gap | 타일 아래와 '확인하지 못한 자료' | 이번 회차에 확인하지 못한 범위와, 작업이 회차마다 하지 않거나 할 수 없는 확인 |

화면이 기록 시각을 왼쪽 칸에 한국시간으로 표시하므로, 작성 작업은 그 시각을 제목에 다시 쓰지 않습니다. 출처 목록에는 OKX, DDHQ, FRED처럼 기관 이름과 주소가 자동으로 표시되므로 본문에서 URL을 설명하지 않아도 됩니다. 본문과 evidence에서 빈 줄로 나눈 부분은 각각 한 단락으로 표시되고, 빈 줄이 없는 긴 글이나 지나치게 긴 단락은 화면이 문장 경계에서 다시 나눕니다.

## kind 어휘

kind는 독자에게 "이 기록이 상황을 바꾸는가"를 알려 주는 신호입니다. 작성 작업은 다음 여섯 가지만 씁니다. '가격·페그 관찰', '부분 점검'처럼 주제나 점검 상태를 나타내던 이름은 kind로 쓰지 않고, 주제는 제목에서 드러냅니다. '기준점'과 '감시 설정'은 기본 자료(data.json)에만 쓰는 이름이므로 작성 작업은 쓰지 않습니다.

| kind | 쓰는 경우 | 예 |
|---|---|---|
| 새 사실 | 이번 점검에서 처음 확인했고 상황 판단을 바꾸는 사실 | 당선 판단, 새 사고 공지, 경보 기준 돌파 |
| 정정 | 앞선 기록의 수치나 판단을 바로잡는 기록 | 이 피드에 이미 적은 피해 추산을 출처가 수정함 |
| 누락 보완 | 이미 일어났지만 앞선 기록에서 빠졌던 사실 | 과거 시각의 당선 판단을 뒤늦게 확인함 |
| 참고 | 수치나 공지가 바뀌었지만 상황 판단은 바꾸지 않는 기록 | 정기 시세, 지연된 거시 자료 |
| 확인 제한 | 원문 접근 실패처럼 이번 회차에 처음 생긴 확인 공백 | 공식 결과 페이지 502 오류 |
| 변화 없음 | 점검했지만 직전 기록과 달라진 내용이 없음 | 같은 공지, 같은 수치 |

화면은 '새 사실'과 '정정'을 가장 눈에 띄게, '확인 제한'과 '변화 없음'을 흐리게 표시하고, 같은 시각의 기록 가운데 흐린 기록을 맨 뒤에 둡니다. Binance, GitBook 같은 대상별 관련 이력은 가장 최근 기록만 펼쳐 보이고 이전 기록을 그 아래에 접어 둡니다. 흐리게 표시하는 기록은 이런 묶음에 넣지 않으므로, 흐린 기록이 묶음의 맨 위에 놓여 실제 사고 기록이 그 아래로 접히는 일이 생기지 않습니다. 목록에 없는 kind도 화면에 나타나지만, 꼬리표 테두리나 배경 없이 일반 글자로 보입니다.

kind는 다음 기준으로 고릅니다.

- 수치나 공지가 바뀌었지만 판단이 그대로이면 '참고'로, 점검한 내용이 직전 기록과 같으면 '변화 없음'으로 씁니다. '직전 기록'은 같은 대상을 다룬 이 범주의 가장 최근 피드 기록을 뜻합니다.
- 일부 범위를 확인하지 못한 회차에는 checkStatus를 partial로 정하고 gap에 적습니다. 그 실패가 처음 생긴 회차에만 '확인 제한' 기록을 한 건 더하고, 실패가 이어지는 동안에는 gap에만 적습니다. 원문 점검이 전부 실패한 회차에는 README 절차대로 이전 observedAt을 유지하고 피드 기록을 더하지 않습니다.
- '누락 보완'과 '정정' 기록의 at도 이번 점검 시각으로 정합니다. 사건이 일어난 시각은 본문에 쓰고, 바로잡는 앞선 기록은 evidence에서 그 기록의 시각과 제목으로 밝힙니다.

## 변화 없는 점검

1. 직전 기록 이후 달라진 내용이 없는 대상은 대상마다 기록을 쓰지 않고, 그 회차의 '변화 없음' 기록 한 건에 이름만 모읍니다. 본문은 무엇이 그대로인지 한 문장으로 쓰고, 앞선 기록의 수치와 유보 문장을 다시 쓰지 않습니다.
2. 새로 쓸 '변화 없음' 기록에 모은 대상이 이 범주의 가장 최근 '변화 없음' 기록과 같으면, 문장 표현이 달라도 피드에 기록을 더하지 않습니다. 이때도 원문을 실제로 점검했다면 observedAt을 그 시각으로 진행시키고 publishedAt, checkStatus, gap을 갱신합니다. 화면은 범주 타일에 실제 관찰 시각을 따로 표시합니다.
3. 기록을 더하지 않은 회차가 이어져 이 범주의 가장 최근 피드 기록에서 6시간이 지나면 '변화 없음' 기록을 한 건 다시 씁니다.

## 문장 규칙

1. 한글 낱말 바로 뒤에 오는 숫자는 띄어 씁니다. "하원241석"이 아니라 "하원 241석", "선두1,796표"가 아니라 "선두 1,796표"로 씁니다. '제9연방항소법원'처럼 서수는 붙여 쓰고, 시간대 약어는 "10:53 UTC"처럼 띄어 쓰며, 수량과 금액에는 천 단위 쉼표를 넣습니다.
2. 본문과 evidence, 요약 필드에 쓰는 시각은 한국시간 "HH:MM"으로 쓰고 초와 밀리초는 버립니다. 원문의 시간대가 판단에 필요할 때만 "19:53(10:53 UTC)"처럼 괄호 안에 한 번 덧붙이고, 기록 시각과 날짜가 다른 시각에는 "11월 3일"을 붙입니다. 두 시각의 차이는 초를 버린 분 단위 시각끼리 계산합니다. 원문에 시간대가 표시되지 않은 시각은 한국시간으로 바꾸지 않고 본문에 쓰지 않으며, 꼭 밝혀야 하면 evidence에 원래 표기대로 옮기고 시간대 표시가 없다는 점을 함께 적습니다. at, observedAt, publishedAt 같은 JSON 시각 필드는 계약대로 UTC 형식을 유지합니다.
3. 제목에는 날짜와 시각을 쓰지 않습니다. 다만 "오전 9시 대비"처럼 수치의 기준을 밝히는 시각은 쓸 수 있으며, 이때도 제목이 숫자로 시작하지 않게 합니다. '점검', '재확인', '대조'처럼 감시 작업이 한 일이나 '…미확인' 같은 유보는 제목에 덧붙이지 않습니다.
4. 본문과 evidence, body, unknown, gap은 "~다"로 끝나는 완결된 문장으로 씁니다. "축소", "미확인", "동일"처럼 명사로 문장을 끝내지 않습니다.
5. 엠대시(—)는 어느 필드에도 쓰지 않습니다. 제목에서는 쉼표나 조사로, 문장에서는 쌍점이나 접속사로 바꿉니다.
6. 가운뎃점(·)은 대등한 항목 두세 개를 나열할 때만 씁니다. 대결, 비교, 항목마다 값이 따로 붙는 관계는 조사로 나타냅니다. "Holscher546,587표·Masterson541,030표"가 아니라 "Holscher 후보는 546,587표, Masterson 후보는 541,030표를 얻었다"로 씁니다.
7. 본문의 주어는 시장, 후보, 기관, 계정처럼 감시하는 대상이나 그 대상에서 일어난 일로 정합니다. 감시 작업이 한 일("조회했다", "대조했다", "재점검했으며")은 evidence에 쓰고, 본문에서는 "조회 시점보다 N분 앞선 값이다"처럼 점검 시각을 기준점으로만 씁니다. 공식 확인되지 않은 주장은 "~라고 주장했다"처럼 주장한 주체를 주어로 씁니다.
8. 출처와 주체는 '작성자', '은행 홈페이지'처럼 모호하게 쓰지 않고 이름을 밝힙니다.
9. 유보 문장은 본문에 한 문장까지만 둡니다. 독자가 가장 오해하기 쉬운 한계 하나를 고르고, "~로 해석하지 않는다", "~와 구분한다" 같은 작성 원칙은 evidence에 씁니다. 회차마다 같은 확인 한계는 본문에 되풀이하지 않고 gap이나 unknown에 한 번 둡니다. 이런 한계는 그 기록의 내용이 어디까지 확인된 것인지 밝혀야 할 때만 evidence에 씁니다.
10. 접근 승인 처리, 도구 오류, 저장과 배포 경로 같은 감시 작업 내부 사정은 어느 필드에도 쓰지 않습니다. 실패는 "그 페이지가 이번 점검에서 열리지 않았다"처럼 결과만 씁니다.
11. 수치는 판단에 필요한 자릿수까지만 씁니다. 등락률은 소수 둘째 자리까지, 페그 이탈은 bp 단위로 소수 첫째 자리까지 쓰고, 원자료는 sources로 연결합니다. 추산이나 분석에서 나온 수치에는 추산한 주체와 기준 시점을 같은 문장에 씁니다.
12. 한 기록에는 변화 한 가지만 담습니다. 서로 다른 대상에서 생긴 변화는 기록을 나누고, 그 변화를 이해하는 데 필요한 다른 대상의 수치만 둘째 단락에 맥락으로 씁니다.

## 단락 나누기

본문(text)이 세 문장 이상이면 빈 줄로 단락을 나눕니다. 한 단락은 한두 문장으로 쓰며, 첫 단락에는 이번에 바뀐 핵심을 두고, 다음 단락에는 세부 수치와 맥락을, 마지막 단락에는 독자가 오해하기 쉬운 한계를 둡니다. 앞 문장을 받는 문장("이는 …", "두 값은 …")이나 바로 앞 수치의 한계를 설명하는 문장은 앞 문장과 같은 단락에 둡니다. 이 결속 규칙이 단락 순서와 충돌하면 같은 단락에 두는 쪽을 따릅니다. evidence도 세 문장이면 같은 방식으로 나누되, 단락의 순서는 위 표에 적은 evidence의 순서를 따릅니다. 범주 요약 필드는 한 단락으로 씁니다.

JSON 문자열 안에서는 단락 사이에 `\n\n`을 넣습니다. 여기서 `\n` 하나는 역슬래시와 n 두 글자로 적는 표기이며, 실제 줄바꿈 문자를 문자열 안에 넣으면 파일 전체가 JSON으로 읽히지 않아 화면이 그 범주의 새 자료를 모두 거부합니다. 반대로 역슬래시를 두 번 적은 `\\n`은 화면에 글자 그대로 보입니다. 저장한 파일이 JSON으로 읽히지 않으면 같은 회차 안에서 바로 고쳐 다시 저장합니다. 이것은 게시한 기록을 고쳐 쓰는 일이 아니라 읽을 수 없는 파일을 되돌리는 일입니다.

~~~json
{ "text": "첫 단락의 핵심 문장이다.\n\n둘째 단락의 세부 수치와 맥락이다. 이는 앞 문장을 받는 문장이다.\n\n마지막 단락의 한계 문장이다." }
~~~

화면은 빈 줄로 나눈 부분을 각각 한 단락으로 표시합니다. 줄바꿈 하나는 문장 끝(. ? ! :) 뒤에 있을 때만 단락을 나누고, 문장 중간의 줄바꿈은 공백으로 봅니다. 빈 줄이 없는 긴 글과 데스크톱에서 약 다섯 줄을 넘는 단락은 화면이 문장 경계에서 다시 나누며, 인용부호나 괄호 안에서는 나누지 않습니다. 자동 분할은 글자를 바꾸지 않지만 문장의 뜻까지 알지는 못하므로, 뜻에 맞는 단락은 작성 작업이 직접 나눕니다.

## 범주 요약 필드

headline은 제목 규칙대로 지금 상황의 핵심을 한 줄로 쓰고, 관찰 시각을 넣지 않습니다. 화면이 headline 위에 실제 관찰 시각을 따로 표시하기 때문입니다. body에는 지금 상황을 쓰고 "보존한다", "혼합하지 않는다" 같은 작업 설명을 쓰지 않습니다. unknown과 gap은 위 표의 역할대로 나눠 쓰고 같은 사항을 두 필드에 겹쳐 쓰지 않으며, 피드 기록에 없는 사건을 요약 필드에서 처음 언급하지 않습니다.

## 고쳐 쓴 예

범주별 예시 다섯 건과 각 예시에서 고친 점은 [docs/feed-writing-prompts.md](feed-writing-prompts.md)에 있습니다. 여기서는 성격이 다른 두 건을 보여 줍니다. 두 예시 모두 계약 검증과 `npm run lint:feed` 점검을 통과합니다.

## 점검 방법

`npm run lint:feed`는 범주별 최신 회차의 기록과 요약 필드에서 띄어쓰기, 시각과 숫자 표기, 문장 종결, 가운뎃점, 엠대시, 문장 수와 단락, kind 어휘를 점검하고, JSON으로 읽히지 않는 범주 파일도 알립니다. 경고는 게시를 막지 않으며, 게시 계약의 검증은 지금처럼 `npm run validate`가 맡습니다. 본문의 주어를 무엇으로 정했는지, 유보 문장을 몇 개 두었는지, 한 기록에 변화 한 가지만 담았는지처럼 문장의 뜻을 읽어야 판단할 수 있는 규칙은 이 점검이 확인하지 못합니다.

~~~sh
npm run lint:feed
node scripts/lint-feed-style.js --all
node scripts/lint-feed-style.js --strict
~~~

`--all`은 범주 파일의 모든 기록을 점검하고, `--strict`는 경고가 하나라도 있으면 실패 코드로 끝납니다.
